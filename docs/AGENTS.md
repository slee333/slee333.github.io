# Repository Guidelines

## Project Structure & Module Organization
The GitHub Pages site lives under `docs/`. Author-facing pages use numbered Markdown files (e.g., `docs/0_about.md`) for manual ordering, while new posts belong in `_posts/` using the Jekyll date slug format. Shared snippets sit in `_includes/` and `_layouts/`, and structured data for menus and socials lives in `_data/`. Styling extends Minima through `assets/css/style.scss`, which imports the partials in `_sass/custom/` (`_tokens.scss` holds every color, width and font; one partial per area: header, footer, home, category, post, about, comments, login, error). Companion scripts live in `assets/js/`. Fonts come from the Pretendard CDN (see `_includes/head.html`); do not add font files to the repo. Do not edit `_site/`; it is regenerated by the build.

## Build, Test, and Development Commands
Run `bundle install` inside `docs/` to sync Ruby gems. Use `bundle exec jekyll serve --livereload` for local preview on `http://127.0.0.1:4000`, and `bundle exec jekyll build` to produce the static site in `_site/`. `bundle exec jekyll doctor` surfaces configuration issues before pushing. When pulling content from Notion, call `python new_blog_workflow.py --help` to see the available automation flags.

## Coding Style & Naming Conventions
Front matter keys follow lowercase snake_case and ISO-8601 timestamps; keep summaries under 160 characters for SEO. Name new posts `YYYY-MM-DD-title.md` and prefer kebab-case anchors for internal links. Markdown files use one blank line between sections and fenced code blocks with language hints. SCSS inherits Minima conventions: two-space indentation, tokens in `_sass/custom/_tokens.scss` (read them with `var(--…)`), and new styles added to the matching partial in `_sass/custom/` rather than inline `<style>` blocks in layouts or pages. Write JavaScript with camelCase functions and avoid global variables; encapsulate helpers in IIFEs when adding new files. Python utilities observe PEP 8 with 4-space indentation.

## Testing Guidelines
Before committing, ensure `bundle exec jekyll build` completes without warnings and spot-check the generated `_site/` pages locally. For content updates, proof bilingual pages (`*_en.md`, `*_es.md`) to keep translations in sync. If `new_blog_workflow.py` is modified, run it against a staging Notion page to confirm front matter and asset uploads succeed.

## Commit & Pull Request Guidelines
Follow the existing history by using short, imperative commit titles such as `update footer icons`; add details in the body when necessary. Squash trivial fixups before opening a PR on `gh-pages`. Each PR should summarize the change, reference any Notion task or GitHub issue, and include before/after screenshots for visual tweaks. Request review once `bundle exec jekyll build` has been re-run and the diff only contains intentional Markdown, asset, or config updates.

## Environment & Secrets
Populate `.env` with Notion and Cloudinary credentials before running automation; never commit that file. Use scoped tokens with upload-only permissions where possible, and rotate them immediately if logs show unauthorized access.
